# agent-spatial-toolkit — v1 design

**Status:** Draft, awaiting review.
**Date:** 2026-05-03
**Decision authority:** cameronzucker, with collaborative drafting from Claude.

---

## 1. Motivation

LLM agents reason poorly about spatial relationships from photos. When you ask an agent to "design a case for this Raspberry Pi HAT," the agent can describe what it sees correctly but cannot reliably place mounting holes, predict where connector cutouts go, or understand which corner of a PCB is which. This shows up as:

- Hallucinated component orientations
- Connectors placed on the wrong edge of the wrong face
- Mirror-image errors where left/right or front/back gets flipped
- Iteration loops where each correction introduces a new error elsewhere

The root cause is that the agent is doing pure visual interpretation: looking at pixels, forming a textual description, and translating that description into geometry. The translation is lossy.

**This toolkit replaces the lossy translation with structured measurement.** The user (or the agent, prompting the user) clicks features in photos. The toolkit applies classical computer-vision math (PnP + multi-view triangulation) to derive `(X, Y, Z)` coordinates in millimeters in a part-local reference frame. The agent then reasons over a labeled feature dictionary instead of pixel data.

The model is **a software CMM**: operator-driven measurement of named features on a known part. The output is a compact, semantic, provenance-rich JSON file — not a 3D mesh, not a generative shape, not a dense point cloud.

## 2. Scope

### In scope for v1 (`v0.1.0`)

- **Single-page browser wizard** for annotation, served by a local Flask server
- **Multi-view triangulation** of clicked features (γ-mode), gracefully degrading to **planar pose estimation** (β-mode) for single-photo sessions
- **Camera distortion handling** via either user-supplied chessboard calibration or a generic FOV-class fallback with explicit warnings
- **Output**: `annotations.json` with full provenance plus reprojection-overlay PNGs for visual validation
- **Two invocation modes**: LLM-orchestrated (via skill primitive) and standalone CLI (for batch / headless use)
- **Distributed as**: a self-contained git repo (this one), MIT-licensed, with optional plugin packaging on top for Claude Code users

### Out of scope for v1, deferred to later versions

- **Templates layer** (Pattern C from brainstorm): per-part-class prescriptions for required photos and expected features. Useful but not blocking. Plan to ship in v0.5+.
- **Self-calibration via bundle adjustment**: joint pose + distortion estimation. v1 leans on chessboard calibration as the accuracy path.
- **Downstream emitters**: converters from `annotations.json` to specific CAD formats (parametric YAML, OpenSCAD, KiCad mechanical layer). Out of scope; user/LLM does this case-by-case in v1.
- **Bundled per-camera distortion database**: rejected during brainstorm — unmaintainable, can't be verified, and a chessboard calibration is more accurate per-session anyway.
- **Live AR / mobile capture**: photos are captured externally with the user's preferred camera and uploaded.
- **Feature auto-detection** (SIFT/ORB matching across photos): not needed; the human provides correspondence.

### Explicitly *not* the goal

- Producing 3D meshes or point clouds (not photogrammetry)
- Replacing CAD tools (the toolkit emits *measurements* that drive CAD; it does not author geometry)
- Hallucinating shapes from limited input (not generative)

## 3. End-to-end user experience

### Step 0 — Photo capture (out of browser, in the user's phone/camera)

The toolkit (or the orchestrating agent, if there is one) instructs the user via a printable spec sheet:

> **Lens choice (most important):**
> - If your phone has multiple lenses, **use the telephoto** (3x or 5x). Distortion is much less than the default wide-angle.
> - **Avoid ultrawide entirely.**
>
> **Framing:**
> - Center the part. Distortion is worst at frame edges.
> - Fill the frame ~60–70%.
>
> **Coverage:**
> - Take at least 3 photos from substantially different angles. More is better.
> - Every feature you want to label must be visible in **≥ 2 photos** for true 3D triangulation. Features visible in only 1 photo will be flagged `z_assumed`.
>
> **Calibration (recommended):**
> - Print the included chessboard PDF. Photograph it once with the same lens you used for the part. This becomes the calibration reference for the session.
> - If skipped, the toolkit uses a generic FOV-class profile and warns about reduced accuracy.
>
> **Consistency:**
> - Same camera + lens for all photos in a set.
> - Sharp focus on the part.
> - Avoid glare on glossy components.

For v1, all photo capture happens *outside* the toolkit — the user takes photos with their phone, drops them in a folder, and points the toolkit at that folder. The spec sheet is generic; per-part-class spec sheets ship with the templates layer in v0.5+.

### Step 1 — Invoke the toolkit

Two entry points share the same backend:

**Agent-orchestrated** (typical case):

```
Agent: invoke_skill("agent-spatial-toolkit", args={
    "part_id": "x1207",
    "photos": ["refs/x1207-top.jpg", "refs/x1207-side.jpg", "refs/x1207-iso.jpg"],
    "chessboard_photo": "refs/chessboard_capture.jpg",   # optional
    "hint": "Pi-style HAT with corner notch and battery holder"
})

Skill starts server, prints URL.
Agent tells user: "Open http://localhost:NNNN to annotate."
```

**Standalone CLI**:

```
$ agent-spatial-toolkit annotate \
    --part-id x1207 \
    --photos refs/x1207-*.jpg \
    --chessboard refs/chessboard_capture.jpg \
    --out ./annotations/

Server starts, prints URL. User opens browser, completes wizard, JSON is written.
```

### Step 2 — Browser wizard (the heart of v1)

The wizard is a single-page web app served from `localhost`. State lives in the browser; events are POSTed to the server which writes them to a session directory.

**Phase 2a — Upload + validate.**
User sees thumbnails of their uploaded photos. For each, the wizard:
- Parses EXIF (camera make/model, lens identifier, focal length, sensor info)
- Asks the user to confirm the lens used (dropdown populated from EXIF if detected)
- Asks the user to label each photo's view ("top-down", "long-edge-A", "side-iso", "other")
- Performs basic blur/exposure sanity checks (Laplacian variance), warns if a photo looks unusable
- Optionally accepts a chessboard photo and runs `cv2.findChessboardCorners` + `cv2.calibrateCamera` to derive precise intrinsics for the session

**Phase 2b — Reference frame definition.**
User picks the part-local coordinate frame:
- Default suggestion based on a preset convention ("standard PCB origin: bottom-left corner with components facing up; +X along long edge; +Y along short edge toward GPIO header; +Z away from PCB bottom")
- User confirms the suggestion or clicks alternative origins/axes for non-standard parts

**Phase 2c — Per-photo calibration.**
For each photo, the wizard prompts the user to click reference frame anchors:
- Anchors are points whose `(X, Y, Z)` in the part-local frame are *known* (typically PCB corners at `Z = 0`)
- Minimum 3 anchors per photo (4+ is better; 3 collinear points fail)
- After clicks, the server runs `cv2.solvePnP` to compute camera pose
- Wireframe overlay drawn onto the photo using the computed pose lets the user verify "yes, the system understood the orientation"
- If reprojection error > 5 px after multiple attempts, the toolkit flags `intrinsics_suspect` and recommends chessboard calibration

**Phase 2d — Feature labeling.**
For each feature the user wants to capture:
- Click in one photo, type/pick a label, mark which other photos the same feature is visible in
- For the *next* photo where the feature is visible, the wizard shows a side-by-side view (D1): the previously-clicked photo with the labeled point highlighted, and the new photo where the user clicks the same feature
- Ad-hoc additions in any photo can be linked to existing features via a dropdown (D3)
- As soon as a feature has ≥ 2 valid clicks, the server triangulates and stores the result; if the user adds more clicks later, the toolkit re-triangulates with the larger set

**Phase 2e — Validation overlay.**
Once the user marks "I'm done," the server reprojects every triangulated feature back onto every photo and renders an overlay. The user sees their photos with colored markers at every feature's predicted position. Mismatches → user clicks "this is wrong" and is sent back to refine.

**Phase 2f — Emit.**
The server writes:
- `annotations.json` (the canonical artifact)
- `overlays/{photo_id}_overlay.png` (one per photo, useful for human and agent review)
- `events.jsonl` (every click captured during the session, for replay/debug)
- `manifest.json` (a small index of the session's artifacts)

### Step 3 — Agent ingest

If the toolkit was agent-orchestrated, the agent reads `annotations.json` on its next turn. The schema is designed to be agent-friendly: every numeric claim is associated with a confidence indicator (reprojection RMS, max residual, method label) so the agent can reason about which features are trustworthy and which need re-checking.

If the toolkit was CLI-orchestrated, the user takes the JSON to whatever downstream system they're driving (their own scripts, parametric CAD tooling, a different agent, etc.).

### Why this shape

- **Local server, browser UI.** Click-based annotation needs a real GUI. Browser is universally available, modern phones can also run it (the wizard is touch-friendly), and it matches the existing Superpowers-visual-companion idiom.
- **Ephemeral session directory.** Each annotation session is its own folder. No global state. Easy to debug, replay, version-control if the user wants to.
- **Skill is dumb math + UI.** The skill knows nothing about Pi 5s, HATs, USB-C connectors, or any other domain. It provides primitives. The orchestrating agent (or the templates layer in v0.5+) provides domain knowledge.
- **JSONL event stream.** Every click is logged with timestamp + label. Replay is free. Debugging a wrong final answer means re-running the math on the events.

## 5. Geometric pipeline

### 5.1 Pipeline (per session)

```
For each photo P_i:
  1. Parse EXIF, identify camera + lens
  2. Resolve intrinsics (chessboard if available, else FOV-class fallback)
  3. User clicks N anchors at known (X, Y, Z=0) positions
  4. solvePnP(known_3d, clicked_2d, intrinsics) → camera pose
     If anchor reprojection RMS > 5 px:
       flag "intrinsics_suspect" for the photo
       recommend chessboard calibration to user

After all photo poses are known:

  5. For each feature F clicked-and-labeled in K photos:
     If K == 1:
       ray-cast click through camera into part frame
       intersect with Z = z_assumed plane (default 0; user override)
       Output: (X, Y, z_assumed) — flagged "z_assumed"
     If K >= 2:
       triangulatePoints across K viewpoints (DLT + nonlinear refine)
       Output: (X, Y, Z) + per-photo residuals + overall RMS
       If RMS > 4 px:
         flag feature, ask user to verify clicks (probably mislabeled)

  6. Validation phase:
     Render every feature back onto every photo as a colored marker
     User confirms or re-clicks
     Iterate until user says "done"

  7. Emit annotations.json + overlay PNGs + manifest
```

### 5.2 Intrinsics + distortion handling

Distortion modeling is **mandatory** in v1. Skipping it produces silently-wrong numbers. Two-tier strategy:

**Tier A — Chessboard calibration (recommended, max accuracy):**
- User photographs a printable chessboard (PDF ships with the toolkit, both A4 and US Letter sizes) using the same camera + lens as the part photos
- `cv2.findChessboardCorners` detects internal corner positions
- `cv2.calibrateCamera` derives `(fx, fy, cx, cy)` plus 5-parameter distortion `(k1, k2, p1, p2, k3)`
- The resulting profile is stored in the session and reused for that camera+lens

**Tier B — Generic FOV-class fallback (fast, with warnings):**
- Parse 35mm-equivalent focal length from EXIF
- Map to FOV class:
  - `< 22 mm equiv` → ultrawide → reject with strong warning, recommend Tier A or different lens
  - `22–35 mm` → wide → use moderate generic profile
  - `35–70 mm` → normal → use mild generic profile (often sufficient post-correction)
  - `> 70 mm` → telephoto → near-zero distortion assumed
- Output is flagged `intrinsics: profile_source: fov_class_fallback` and the per-feature confidence reflects this

**Auto-promotion behavior:**
If anchor reprojection RMS exceeds 5 px across multiple photos despite reasonable user clicks, the toolkit auto-flags `intrinsics_suspect` and recommends switching to Tier A. Tier B never silently produces garbage — it fails toward Tier A.

### 5.3 Reference anchors per photo

- **Minimum 3 non-collinear anchors per photo** for `solvePnP` to converge
- **4+ recommended** for accuracy; reprojection error is the quality signal
- Anchors are points at *known* `(X, Y, Z)` in the part-local frame — typically PCB corners (`Z = 0`) but the user can declare any known point as an anchor
- Photos that fail to fit a reasonable pose (high RMS) are flagged `uncalibrated` and are excluded from triangulation. Their clicked features become "annotation-only" — useful for visual notes but don't contribute to 3D output

### 5.4 Multi-photo correspondence

The user, not the algorithm, provides feature correspondence across photos. The wizard enforces this by:

- **Side-by-side guided cycle (D1):** when entering a new photo, show the previous photo with the not-yet-relabeled features highlighted; user clicks the same feature in the new photo
- **Ad-hoc dropdown (D3):** at any time, the user can add a feature to a photo and pick from a dropdown of existing labels to link it as the same feature

This eliminates the entire SIFT/ORB matching layer that photogrammetry tools spend significant complexity on. We don't need it because the human is the matcher.

### 5.5 Output coordinate frames

| Frame | Purpose | Where it appears |
|---|---|---|
| Photo pixel | 2D coordinates in each photo (origin top-left) | Click capture, EXIF metadata |
| Camera frame | Per-photo 3D, intermediate | Hidden from user; pose `(rvec, tvec)` |
| Part-local | Single global 3D, mm | **The output.** Origin and axis directions chosen during reference-frame definition. |

The canonical artifact is `annotations.json`. Schema is versioned via `schema_version`. Provenance is preserved at every level — every numeric claim points back to which click in which photo produced it.

### Agent consumption

The agent reads `annotations.json` directly via the framework's file-read primitive, parses the JSON, and reasons over it. Three tiers of consumption are envisioned:

1. **Direct read** — agent parses JSON, produces downstream artifacts (CAD YAML, OpenSCAD, technical brief). v1 supports this fully.
2. **Helper module** (`agent_spatial_toolkit.load`) — Python convenience for post-skill scripts. Ships with v1.
3. **Templated downstream emitters** — converters to specific CAD formats. Out of scope for v1.

### Schema design principles (for review)

- **Self-describing**: someone reading the JSON cold (no toolkit, no docs) understands the fields
- **Provenance-rich**: every numeric claim points back to which click in which photo
- **One canonical format**: no parallel terse/detailed schemas; downstream consumers project as needed
- **Versioned**: `schema_version: 1` at the top; future changes get new versions and migration scripts
- **No abstract confidence scores**: numeric thresholds for "is this trustworthy" belong in downstream consumers, not embedded in the data

## 8. Distribution & packaging

### Strategy: A4 (own repo + plugin packaging on top)

- **Primary**: this git repo, MIT-licensed, suitable for hand-install on any agentic framework via `git clone && pip install -e .`
- **Secondary**: layered plugin packaging for Claude Code users (Superpowers-style) once core works
- **Self-contained**: no calibration database to maintain, no cloud dependencies, no external services. The toolkit ships with everything it needs (chessboard PDFs, code, docs).

### Dependencies

| Package | Purpose | aarch64 wheels available |
|---|---|---|
| `opencv-python` | PnP, triangulation, chessboard, undistortion | Yes |
| `Flask` | Local HTTP server | Yes |
| `numpy` | Math | Yes |
| `Pillow` | Image I/O, EXIF | Yes |
| `PyYAML` | Schema serialization (alongside JSON) | Yes |
| `pyexiv2` (optional) | More-detailed EXIF | Yes |

All dependencies are pure-Python or have aarch64 wheels.

### Privacy posture

- All processing local; no telemetry; no cloud calls
- Server binds to `127.0.0.1` by default; `--host 0.0.0.0` available with explicit warning
- Photos remain on the user's filesystem; the toolkit reads but never uploads them
- Session directories are written under `~/.spatial-annotations/` by default; `--out` flag overrides

## 9. Failure modes & error handling

### Calibration failures

| Failure | Detection | UX |
|---|---|---|
| EXIF missing or unparseable | EXIF parser returns nothing | Prompt user to confirm camera + focal length manually; warn that accuracy degrades |
| Camera/lens unrecognized | Lookup against EXIF returns no match | Fall back to FOV-class generic; loud warning |
| Chessboard photo doesn't detect corners | `cv2.findChessboardCorners` returns failure | Show user the failed detection visually; suggest re-photographing |
| Anchor PnP fails (high RMS) | Reprojection RMS > 5 px on 4 anchors | Highlight wireframe overlay so user sees what the system computed; offer re-click of anchors |
| Anchor PnP fails repeatedly | RMS still high after 2 retries | Flag `intrinsics_suspect`, recommend Tier A chessboard if user is on Tier B |

### Triangulation failures

| Failure | Detection | UX |
|---|---|---|
| Feature clicked in only 1 photo | `K == 1` at finalize time | Mark `z_assumed`; surface in `quality_summary.z_assumed_count` |
| Triangulation RMS high (> 4 px) | Reprojection check post-triangulation | Flag the feature, show per-photo residuals; user can identify the misclicked photo |
| Photos with conflicting poses | Cross-photo consistency check | Highlight which photo's pose is inconsistent; allow user to recalibrate or remove |

### Wizard interruption

| Scenario | Behavior |
|---|---|
| User closes browser mid-session | State persists in `state.json`; reopening URL resumes |
| User closes browser, kills server | Re-run with same `--part-id` and original session timestamp resumes |
| Server idle > 30 min | Auto-shutdown; resume requires re-invocation |

### Edge cases

- **Symmetrical PCBs** (square outline): PnP can have rotational ambiguity. Default solver picks the pose with positive Z; user can flip if wrong.
- **Wide-angle ultrawide photos** (FOV > 100°): rejected at upload with explicit guidance.
- **Photos with no recognizable anchors**: marked `uncalibrated`; clicked features become annotation-only.

## 11. Cross-model adversarial validation

The toolkit is explicitly designed to work across multiple agentic frameworks (Claude Code, Codex, Gemini CLI, Cline, Continue, etc.). That cross-vendor portability is **not free** — it has to be tested deliberately, because each model family has its own conventions for skill invocation, JSON parsing, and downstream artifact production.

### What "cross-model validation" means here

Three distinct concerns, each tested separately:

**11.1 Skill invocation parity.** Can each agent framework actually invoke the toolkit?
- The toolkit ships with a `SKILL.md` that names `agent-spatial-toolkit` and describes its behavior. Different frameworks read this file differently:
  - Claude Code reads it as a `<skill>` primitive
  - Codex reads it as a tool definition (function schema-style)
  - Gemini CLI uses `activate_skill`
  - Continue / Cline use plugin manifests
- For each target framework, we need a manifest or shim that maps `SKILL.md` to the framework's invocation convention. **Not all of these can come from the toolkit alone** — some require per-framework wrapping.
- v1 ships first-class support for **Claude Code (Skill primitive) and standalone CLI**. Other frameworks get a **"compatibility note"** in the README explaining how to wire them up.

**11.2 SKILL.md interpretation parity.** Given the same SKILL.md, do different models interpret the *intent* equivalently?
- Each model is asked to summarize the skill in its own words. We compare summaries for drift.
- Specific test prompts (e.g., "I have photos of my X1207 HAT and need a case design — what should I do?") are run through each model. We check that each one decides to invoke `agent-spatial-toolkit` rather than improvising.
- Adversarial prompts: cases where invoking the toolkit is wrong (e.g., "I already have the STEP file"). Models that wrongly invoke get the SKILL.md updated.

**11.3 Output consumption parity.** Given an `annotations.json`, can each model produce equivalent downstream artifacts?
- A canonical `annotations.json` (golden fixture) is fed to each model with a downstream prompt: "Produce a parts-library YAML for the X1207 from this annotation."
- The outputs are diffed for semantic equivalence (not byte-exact — different models phrase things differently). The test passes if every output:
  - Contains all features from the annotation
  - Preserves coordinate values to within rounding
  - Doesn't hallucinate features that weren't in the annotation
- Disagreements drive schema refinement: if Model X consistently misinterprets a field, the field name or schema documentation changes.

### Validation gating

| Phase | What runs | Frequency |
|---|---|---|
| **Pre-merge (PR)** | Unit + integration tests (Python only — no model calls) | Every commit |
| **Pre-release (release branch)** | All of the above + cross-model validation suite (Claude + GPT-4o + Gemini Pro at minimum) | Every release candidate |
| **Quarterly** | Full re-validation against latest model versions; SKILL.md drift check | Cron |

Cross-model tests cost API tokens. v1 budgets for one full pre-release run per release candidate (~$5–20 in API costs). They run via a `bin/validate-cross-model.sh` script, not in CI by default — release manager runs it manually before tagging.

### Per-model adapter strategy

The toolkit's *core* is model-agnostic (Python + Flask + JSON). The only model-specific pieces are:

```
adapters/
├── claude_code/
│   ├── plugin.json           # Superpowers-style plugin packaging (optional)
│   └── skill_link.md         # symlinks SKILL.md into ~/.claude/skills/
├── codex/
│   ├── tool_schema.json      # function-calling tool definition
│   └── invocation_example.md # how to invoke via Codex's API
├── gemini_cli/
│   └── activate_template.md  # how to activate via Gemini CLI
└── generic/
    └── README.md             # for users on bespoke frameworks: how to wrap CLI
```

Each adapter is small (a few hundred bytes) and is *optional* — the toolkit works perfectly with no adapter at all if invoked via CLI. Adapters exist to reduce friction for users on specific frameworks.

### What we explicitly DON'T do

- **No model-specific schema variants.** `annotations.json` is the same on all platforms. If GPT-4o struggles with some field, we fix the schema, not fork it.
- **No runtime model gating.** The toolkit doesn't refuse to run on certain frameworks. If your framework can read JSON, it can consume the output.
- **No proprietary integrations.** Everything is open-spec, MIT-licensed, runnable without API keys for the local server portion.

### Risks

- **Drift between model versions.** GPT-4o today and GPT-5 next year may interpret SKILL.md differently. The quarterly validation cycle catches this.
- **Smaller models / open-source models.** Llama, Qwen, Mistral, etc. are out of scope for v1 cross-model testing. They're likely to work but unverified. If the project gains traction, community contribution can extend the validation matrix.
- **Adapter rot.** Plugin packaging conventions (Claude Code's, Codex's, etc.) evolve. The adapter dir is the maintenance burden; we minimize it by keeping adapters thin.

## 12. Decisions log

Captured here so the design's structural choices are auditable, with one-line reasoning.

| # | Decision | Rationale |
|---|---|---|
| D1 | Scope C (visual reasoning companion, broad) | Rejected scope A (PCB-only) as too narrow; rejected B (medium) as a hedged middle. Build the most useful thing. |
| D2 | Pattern C interaction (B-first, templates layered) | Templates are useful but should layer on top of a working primitive layer; keeps v1 lean |
| D3 | v1γ with graceful degradation | True 3D is the value-add; degradation handles single-photo case without complicating the API |
| D4 | Two-tier intrinsics (chessboard + FOV-class), no database | A bundled DB is unmaintainable; chessboard is per-session ground truth and self-contained |
| D5 | Single-page UI for v1 | State-heavy wizard maps poorly to multi-page Superpowers-style; revisit if the SPA becomes unwieldy |
| D6 | Reference frame: B3 (preset + click-override) | PCBs benefit from preset; non-standard parts need flexibility |
| D7 | Anchors: C2+C3 (3+ anchors with reprojection validation) | Permissive minimum + auto-fallback handles oblique side photos cleanly |
| D8 | Correspondence UX: D1+D3 (guided cycle + dropdown) | Side-by-side cycle for known features; dropdown for ad-hoc additions |
| D9 | Persistence: E3 (timestamped sessions, no merge) | Simplest and matches "no global state" architecture; merging is a v1.5 feature |
| D10 | Distribution: A4 (own repo + plugin layered later) | Maximum portability; doesn't lock to one agentic framework |
| D11 | Name: agent-spatial-toolkit | "Agent" signals LLM-orchestrated; "spatial" is the domain; "toolkit" is honest sizing |
| D12 | License: MIT | Maximum permissiveness for downstream reuse |
| D13 | Distortion is mandatory in v1 | Skipping distortion silently degrades accuracy and bias the pose estimates; must be modeled |
| D14 | Cross-model adversarial validation is a release gate | The toolkit's portability promise (Claude / Codex / Gemini / others) must be tested deliberately, not assumed; quarterly re-validation catches model-version drift |

## 13. Future work

Numbered for traceability, not prioritized.

1. **Templates layer (v0.5)** — per-part-class prescriptions: required photos, expected features, default reference frames, downstream-emitter hooks. Ships with starter templates for Pi-style HATs, M.2 NVMe modules, common SBCs.
2. **Self-calibration via bundle adjustment (v1.0)** — joint pose + intrinsics + features optimization. Unblocks accuracy when no chessboard is available.
3. **Downstream emitters (v1.0+)** — `annotations.json` → parametric YAML, OpenSCAD modules, KiCad mech layer, FreeCAD STEP scaffolds. Plugin architecture so new emitters can be added without touching the core.
4. **Mobile capture companion** — phone app that guides photo capture in real time, ensures sufficient angular baselines, computes intrinsics on-device.
5. **Reprojection-guided refinement** — after first-pass triangulation, the wizard could highlight the reprojected position of each feature in subsequent photos and suggest the user "verify this is exactly where the feature is in this photo." Faster than full re-clicking.
6. **Distortion-aware feature subpixel refinement** — after a click, snap to nearest detected edge/corner for sub-pixel accuracy. Requires careful UX so the snap doesn't surprise the user.
7. **Library / catalog of pre-annotated parts** — community-contributed `annotations.json` files for common parts (Pi 5, Arduino Uno, ESP32 dev boards). Users skip annotation if their part is already in the library.
8. **Validation harness** — given a verified CAD file (STEP, STL), the toolkit can compare annotations against ground truth and produce a calibration delta. Useful for power users and library curators.
